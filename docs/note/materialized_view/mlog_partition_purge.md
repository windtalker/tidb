# Materialized View Log Partition Purge (Design Notes)

This document records the current design discussion for reducing
`PURGE MATERIALIZED VIEW LOG` resource usage by reclaiming old data through
partition DDL instead of row-by-row `DELETE`.

The notes below are intentionally scoped to the currently agreed direction.
Items that are still undecided are listed explicitly in the final section.

## Motivation

The current mlog purge path deletes eligible rows in batches:

- eligibility is defined by `_tidb_commit_ts <= safePurgeTSO`
- physical reclamation is done by repeated `DELETE ... LIMIT ...`

This works for correctness, but large mlog tables can still make purge
expensive. The target here is different from "delete as much as possible":

- it is acceptable for old mlog rows to remain longer
- the primary goal is to avoid significant extra resource usage caused by purge

Therefore the preferred direction is:

- drop whole old partitions when it is 100% safe
- otherwise do nothing in this purge round

No row-by-row delete fallback is planned in the first version.

## Scope

This is an explicit opt-in capability for new materialized view logs.

The first version does not attempt to:

- online-migrate existing non-partitioned mlogs into partitioned mlogs
- provide automatic transparent conversion for existing users
- optimize "cannot drop yet" cases by falling back to batched delete

## Chosen Direction

### 1. Add an internal `start_ts` column

Partition pruning and future partition maintenance should be based on
transaction `start_ts`.

The mlog gains one extra internal column:

- `start_ts bigint unsigned not null`

This column:

- is not part of user tracked columns
- is not part of MV refresh semantics directly
- exists only to support mlog partition routing and low-cost purge

`commit_ts` is not used as the partition key because it is only known at commit
time. It can still be used inside purge-time checks through `_tidb_commit_ts`.

### 2. Partition by fixed-width `start_ts` buckets

The mlog is partitioned by range on `start_ts`.

The design uses fixed-width TSO buckets. A typical deployment target is
"one day per bucket", but the exact bucket anchor still needs to be finalized.

The chosen partitioning style is:

- range partitioning on `start_ts`
- interval partitioning so new future partitions can be generated by boundary
  DDL instead of spelling every partition manually

Conceptually:

```sql
PARTITION BY RANGE(start_ts)
INTERVAL (<bucket_width>)
FIRST PARTITION LESS THAN (<first_upper>)
LAST PARTITION LESS THAN (<last_upper>)
```

Important constraint:

- do not use `MAXVALUE PARTITION` in this design, because future growth is
  maintained with `ALTER TABLE ... LAST PARTITION LESS THAN (...)`

### 3. Maintain future partitions in `mvservice`

Even with `INTERVAL` partitioning, TiDB does not auto-create future partitions
on insert. Future partitions must still be added through explicit DDL.

This responsibility belongs to `mvservice`, not to purge itself.

The current agreed policy is:

- keep at least 3 days of future partition headroom
- use a dedicated background keeper in `mvservice`
- extend partitions with `ALTER TABLE ... LAST PARTITION LESS THAN (...)`

This is intentionally separate from purge:

- partition extension prevents future writes from failing
- purge reclaims already safe historical partitions

These two maintenance loops should not be coupled.

### 4. Drop-only purge

Purge no longer tries to reclaim rows eagerly.

The first version uses only this behavior:

- if one or more old partitions are fully safe to reclaim, drop them
- otherwise return success without deleting rows

The design explicitly avoids row-delete fallback.

Rationale:

- the main goal is low resource usage, not immediate reclamation
- with coarse partitions such as daily buckets and frequent purge scheduling,
  most rounds would fall back anyway
- no-op success is acceptable for this feature

## Safe Drop Conditions

For an old partition `P`, dropping it must satisfy two independent conditions.

### Condition A: no future write can still land in the partition

Let:

- `partition_upper_start_ts(P)` be the exclusive upper bound of `P`
- `minActiveTxnStartTS` be a cluster-wide lower bound of the minimum active
  transaction start ts

Then `P` is sealed only if:

```text
partition_upper_start_ts(P) <= minActiveTxnStartTS
```

This guarantees that no active transaction can later commit a row whose
`start_ts` still belongs to `P`.

### Condition B: all existing rows in the partition are already purge-safe

Current mlog purge correctness is defined by `_tidb_commit_ts <= safePurgeTSO`.

Therefore sealing by `start_ts` alone is not enough. The partition also needs
to satisfy:

```text
all rows in P have _tidb_commit_ts <= safePurgeTSO
```

At implementation time this can be checked by SQL against the candidate
partition, for example through either of these equivalent forms:

- `max(_tidb_commit_ts) <= safePurgeTSO`
- `not exists row with _tidb_commit_ts > safePurgeTSO`

The latter form is often easier to short-circuit.

### Final rule

Partition `P` can be dropped only when both conditions hold:

```text
partition_upper_start_ts(P) <= minActiveTxnStartTS
and
partition_upper_commit_ts(P) <= safePurgeTSO
```

In practice the commit-ts side is derived by query, not by partition metadata.

## Purge Algorithm

The purge path remains serialized by the existing per-mlog purge lock.

Within one purge round:

1. Compute `safePurgeTSO` using the existing MV refresh watermark rules.
2. Read the cluster-wide `minActiveTxnStartTS` lower bound.
3. Start from the oldest partition and check candidates in order.
4. Keep collecting consecutive partitions while both safe-drop conditions hold.
5. Stop at the first partition that fails either condition.
6. If no partition is eligible, return success without physical reclamation.
7. If one or more partitions are eligible, drop them in one purge round.

The purge implementation should try to drop multiple consecutive old partitions
in one round, not just one.

## `LAST_PURGED_TSO` Semantics

`LAST_PURGED_TSO` cannot keep its current "logical progress" meaning if purge no
longer deletes rows by `_tidb_commit_ts`.

For partition-drop purge, `LAST_PURGED_TSO` is redefined as:

- the maximum commit ts among rows physically reclaimed by dropped partitions

The agreed direction is:

- compute this value before executing the partition-drop DDL
- only persist it after the DDL succeeds
- if no partition is dropped in this round, do not advance `LAST_PURGED_TSO`

This preserves the meaning "physically purged up to here".

## Statement Result / History Rows

In the first version, purge row counts do not need to be exact.

The current agreed direction is:

- statement result can report `0 rows`
- purge history can also keep `PURGE_ROWS = 0`

If exact counts become important later, they can be added by extra SQL, but that
is not part of the first design because it would add scan cost back into purge.

## Cluster-Wide `minActiveTxnStartTS`

The design needs a cluster-wide value that is:

- 100% safe
- allowed to be stale
- allowed to be conservative
- not allowed to be greater than the true minimum active txn start ts

The existing GC `ReportMinStartTS` mechanism cannot be reused as-is because it
intentionally applies `tidb_gc_max_wait_time` truncation semantics, which are
acceptable for GC but not acceptable for irreversible partition drop.

The agreed direction is:

- reuse the existing per-node sampling framework so each TiDB node does not need
  a second full scan loop
- compute an additional MV-specific value from the same sampling pass
- do not apply `tidb_gc_max_wait_time` style truncation to the MV-specific value
- enable this extra reporting only when the cluster actually has mlogs using
  this partition-purge feature

Sampling scope should include:

- normal sessions / process list transactions
- internal sessions
- inner transaction tracking

The current design does not require including InfoSchema-only recent ts in this
MV-specific value.

## Serialization Requirements

The following operations should remain serialized per mlog:

- partition-drop purge
- future partition extension
- manual purge
- mlog drop / related DDL that invalidates partition maintenance

The current preferred direction is to keep using the existing per-mlog locking
model instead of introducing a separate distributed coordination mechanism.

## Operational Notes

### Why `INTERVAL + LAST/FIRST PARTITION`

This design prefers interval partitioning because it keeps maintenance boundary
based instead of partition-name based:

- future extension: `ALTER TABLE ... LAST PARTITION LESS THAN (...)`
- old partition reclamation: `ALTER TABLE ... FIRST PARTITION LESS THAN (...)`

This matches the desired mlog lifecycle well.

### Why no delete fallback

The goal is to avoid purge itself becoming a source of significant resource
usage. Since delayed reclamation is acceptable, the first version intentionally
chooses:

- low-cost reclamation when possible
- otherwise no-op success

## Open Items

The following points are intentionally left open for later discussion:

- exact SQL syntax / DDL surface for the user-facing opt-in
- exact fixed-width TSO bucket anchor
- CDC expectations for frequent partition DDL
- whether later versions should expose more partition-maintenance knobs
